# 07. テスト仕様

## 7.1 テスト方針

| 階層 | テスト種別 | アノテーション | 起動範囲 | 目的 |
|---|---|---|---|---|
| Mapper | 単体テスト | `@MybatisTest` | Mapper + DataSource | SQL とマッピングが意図どおりか |
| Service | 結合テスト | `@SpringBootTest` | アプリ全体 | 業務ロジックとトランザクション挙動 |
| Controller | 単体テスト | `@WebMvcTest` | Web 層のみ | リクエスト/レスポンスの形 |

### テスト用 DB

- すべてのテストで `@AutoConfigureTestDatabase` を付与し、接続先を**インメモリ H2** に差し替える。
  → 開発用の `data/scmdb.mv.db` を汚さない。
- Mapper テストでは `@Sql(scripts = {"/schema.sql", "/data.sql"})` でスキーマと初期データを投入する。
  両スクリプトは冪等なため、テストごとに実行しても重複しない。

### トランザクションの扱い

| テストクラス | `@Transactional` | 理由 |
|---|---|---|
| `ItemMapperTest` / `StockMapperTest` / `ShipmentMapperTest` | あり(`@MybatisTest` の既定) | 各テストの更新をロールバックし、テスト間の独立性を保つ |
| `ItemServiceTest` | あり | 同上 |
| `ShipmentServiceTest` | **なし(意図的)** | テストをトランザクションで包むと、業務処理のロールバックを検証できないため。実際にコミットさせ、DB の値で検証する |

> `ShipmentServiceTest` はコミットを伴うため、テストメソッド間でデータが残る。
> そのため、在庫数は絶対値ではなく**実行前後の差分**で検証している。

### 実行方法

```powershell
mvn test                                    # 全件(34件)
mvn test -Dtest=ShipmentMapperTest          # クラス指定
mvn test -Dtest=ShipmentServiceTest#allocateRollsBackWhenStockIsShort   # メソッド指定
```

### 7.2.1 ItemMapperTest(7件)― アノテーション方式 Mapper

| 4 | 動的SQL: 条件を何も指定しなければ WHERE 句ごと消えて全件返る | `findAll` と同件数 |
| 5 | 動的SQL: カテゴリと価格帯を組み合わせるとAND条件になる | カテゴリ一致かつ単価が範囲内 |
| 6 | INSERT すると採番されたIDが引数のオブジェクトに書き戻される | `useGeneratedKeys` の動作確認 |
| 7 | UPDATE / DELETE は更新件数が返る | 戻り値1、更新後・削除後の状態 |

### 7.2.4 ItemServiceTest(5件)― 商品サービス

| # | テストケース | 確認内容 |
|---|---|---|
| 1 | ソート未指定(null)でも既定の並び順で検索できる | 商品コード昇順で先頭が `ITM-1001` |

### 7.2.5 ShipmentServiceTest(8件)― 出荷業務・トランザクション

| # | テストケース | 確認内容 |
|---|---|---|
| 1 | 登録すると出荷番号が採番され、明細ごと保存される | 番号の形式(`SH-20261001-`)、status=登録済、**在庫は不変** |
| 2 | 同じ商品を複数行で入力すると1行にまとめられる | 明細1行、数量が合算(3+4=7) |
| 3 | 引当すると在庫が減り、ステータスが引当済になる | 在庫が10減少、status=引当済 |
| 4 | **在庫不足なら例外になり、先に処理された明細の在庫も元に戻る** | `BusinessException`「在庫が不足」、**両商品の在庫が変化なし**、status は登録済のまま |
| 5 | 引当済を取消すると在庫が戻る | 取消後、在庫が引当前の値に復帰 |
| 6 | 登録済のまま出荷しようとするとエラーになる | `BusinessException`「引当済」 |
| 7 | 引当 → 出荷 の順なら出荷済にできる | status=出荷済、その後の取消はエラー |
| 8 | 明細が空なら登録できない | `BusinessException`「明細」 |

> **#4 が本アプリで最も重要なテスト。**
> 1行目(引当可能)と2行目(在庫超過)を持つ出荷指示を引き当て、
> 例外発生後に**1行目の在庫も減っていない**ことを確認することで、
> トランザクションが正しくロールバックされていることを検証している。

## 7.4 手動確認手順(受入確認)

アプリ起動後、以下を順に実施する。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | `/items` でキーワード「ルーター」を検索 | ルーターを含む商品のみ表示。コンソールに LIKE 付きの SQL が出力される |
| 2 | `/items/new` で商品を登録 | 一覧に追加され、成功メッセージが表示される |
| 3 | 同じ商品コードで再登録 | 「商品コードが重複しています」が表示される |
| 4 | `/stocks` で倉庫を切り替え | 該当倉庫の在庫のみ表示(画面遷移なし) |
| 5 | `/stocks` で入庫を実行 | 在庫数が増え、更新日時が現在時刻になる |
| 6 | `/shipments/new` で明細2行の出荷指示を登録 | 詳細画面へ遷移し、出荷番号が採番されている |
| 7 | 詳細画面で「在庫引当(Ajax)」 | バッジが「引当済」に変わり、`/stocks` で在庫が減っている |
| 8 | 在庫数を超える数量の出荷指示を作成し引当 | 「在庫が不足しています」が表示され、**在庫が1つも減っていない** |
| 9 | 引当済の出荷指示を取消 | バッジが「取消」に変わり、在庫が元に戻る |
| 10 | 出荷済の出荷指示を取消 | 「出荷済の出荷指示は取消できません」が表示される |
